== Why

Facto ships the Valentus theme with several color schemes, and extensions add their own CSS and dynamic UI, such as the search dropdown.
A problem can show up in one scheme or one UI state while everything else looks fine.
`contrast-check` loads the built site in Chrome once per color scheme the paint declares, opens dynamic UI such as search results, and reports WCAG AA failures as errors and near misses as warnings, each with a suggested color.

== Built into Facto (since v0.4.0)

`contrast-check` ({cc-tag}) is a Facto dependency.
The facto-stack extension runs it on the published site after every `antora` build, so you do not add a CI step.
Full reference: {url-cc-docs}[chassis contrast-check docs] and the {url-cc-readme}[package README].

What the default run does:

* *Every color scheme* the paint declares (light and dark for Valentus).
* *Dynamic states* `search-results` and `fixtures`: after the static check, each page is reloaded, a query is typed into the search box (antora-search-chat registers the sample state), and the open dropdown is checked. Motion is reduced and transitions are off, so the end state is what gets measured.
* *Up to 20 pages* (`maxPages: 20`). Each page costs about 10-15 s per scheme with both states, so 20 pages is roughly 8 minutes on a GitHub-hosted runner. Raise it for a nightly run, or list key pages with `pages`.
* *Fail scope `dark-and-states`*: the build fails on WCAG AA *errors* in dark mode, and on errors a dynamic state introduces (a state re-checks the whole page, so a light-mode issue already on the static page is not counted twice).
  Every other finding, light-mode static pages and all warnings, is printed as a report and does not fail the build.
* *Default suppressions* from `lib/contrast-check.suppress.json`, each with a reason and an expiry date.
* *Chrome*: found at the usual Linux, macOS or Windows paths, or set `CONTRAST_CHECK_CHROME`. Without a browser the check is skipped with a warning locally, and fails the build when `CI` is set.

=== Per-site override

Set the pack key `contrastCheck` in the facto-stack extension entry of your playbook:

[source,yaml]
----
antora:
  extensions:
    - require: '@antora-supplemental/facto-stack'
      contrastCheck:
        failOn: error              # error (default) | warning | none
        failScope: dark-and-states # default; `all` also fails light-mode static errors
        maxPages: 20               # default 20
        pages: "index.html,guides/**/*.html"
        schemes: "light,dark"      # default: every scheme
        states: [search-results, fixtures]   # add reveal-hidden for a stricter (noisier) pass
        config: contrast-check.config.json   # default: picked up from the playbook dir
        suppress: contrast-check.suppress.yaml
        json: build/contrast-check.json      # keep the full report
        defaultSuppressions: true            # false drops Facto's reviewed suppressions
        requireBrowser: false                # default: true when CI is set
----

Turn it off with `contrastCheck: false` (or `enabled: false`).
Environment overrides: `FACTO_CONTRAST_CHECK=0` skips the check, `FACTO_CONTRAST_CHECK_FAIL_ON` sets `failOn` and `FACTO_CONTRAST_CHECK_FAIL_SCOPE` sets `failScope`.

A practical rollout for a site that wants a stricter gate: keep the default until dark mode is clean, then set `failScope: all`, and move to `failOn: warning` only if near misses should fail too.

=== GitHub Actions

GitHub-hosted Ubuntu runners already have Chrome, and the check runs inside your existing build step:

[source,yaml]
----
      - name: Build Antora site (includes the contrast check)
        run: |
          npm install
          npx antora antora-playbook.yml
----
== Running it outside Facto (GitLab CI and others)

The CLI needs Node.js 20 or later and Chrome or Chromium.
It finds `/usr/bin/google-chrome`, `/usr/bin/chromium` or Chrome on Windows; otherwise set `CONTRAST_CHECK_CHROME` to the browser path.

=== Install from the git tag

The package installs straight from the chassis git tag; it does not need the npm registry entry.
Add it to your site's `devDependencies`:

[source,json,subs=attributes+]
----
"devDependencies": {
  "@antora-supplemental/contrast-check": "github:antora-supplemental/antora-ui-chassis#{cc-tag}&path:packages/contrast-check"
}
----

Or check out the tag and run the CLI from the checkout, the way the GitHub Action does:

[source,sh,subs=attributes+]
----
git clone --depth 1 --branch {cc-tag} {url-cc-repo}.git .contrast-check
(cd .contrast-check/packages/contrast-check && npm install --no-save --omit=dev --ignore-scripts)
node .contrast-check/packages/contrast-check/bin/contrast-check.js build/site --fail-on none
----

=== GitLab CI example

[source,yaml,subs=attributes+]
----
contrast-check:
  stage: test
  image: node:20
  before_script:
    - apt-get update && apt-get install -y chromium
  script:
    - npm install
    - npx antora antora-playbook.yml
    - npx contrast-check build/site --pages "index.html,**/*.html" --max-pages 50 --fail-on none --json=contrast-check.json
  artifacts:
    when: always
    paths: [contrast-check.json]
----

Common flags: `--pages <list>`, `--max-pages <n>`, `--schemes <ids>` (default every scheme), `--paint <file.css>`, `--config <file>`, `--suppress <file>`, `--show-suppressed`, `--fail-on-stale`, `--json=<file>`, `--quiet`.
Exit codes: 0 clean (under `--fail-on`), 1 failed, 2 usage or setup error.

=== Roll out with --fail-on

[cols="1,3"]
|===
| `--fail-on none` | Report only; never fails. Start here to see the findings.
| `--fail-on warning` | Fails on any finding (same as `--strict`). Use when warnings are close to zero.
| `--fail-on error` | Fails on WCAG AA errors only. The default; the usual end state.
|===

A practical order: `none` while you fix or suppress the first report, then `error` to gate merges.
Move to `warning` only if you also want near misses to fail.
The config key `failOn` sets the same thing.

== Config and suppressions (standalone CLI)

Put `contrast-check.config.json` in the directory the check runs from (it is picked up by default), or pass `--config` / the `config` input.
Unknown keys are an error.
A `suppress` entry accepts a known finding: `reason` is required, and after `expires` (`YYYY-MM-DD`) the entry is ignored and reported as `suppression-expired`.

[source,json]
----
{
  "pages": ["index.html", "**/*.html"],
  "maxPages": 50,
  "failOn": "error",
  "failOnStale": false,
  "suppress": [
    {
      "rule": "color-contrast",
      "selector": ".search-input::placeholder",
      "scheme": ["dark"],
      "reason": "Placeholder text, not content; tracked in #42",
      "expires": "2027-03-31"
    }
  ]
}
----

An entry that matches nothing is reported as `suppression-stale`; add `--fail-on-stale` (`failOnStale: true`) to fail on stale or expired entries.
Prefer `suppress` over `ignore`, which drops findings silently.

=== Inline opt-out

Mark an element (or an ancestor) in your templates or content:

[source,html]
----
<nav class="api-nav" data-contrast-check-ignore="focus-not-visible hover-no-change">
----

The value lists rule ids, aliases or globs; an empty value suppresses every rule.
These show as suppressed by `inline`.
Paint and token findings have no element and need a `suppress` entry.
